# **Model and Router**
# **5 Model Architecture**

---

## **5.1 Semantic Core**

The Semantic Core serves as the central processing unit for generating foundational language responses within Genius LLM v1. It is optimized for high-throughput, distributed inference across the decentralized network.

### 5.1.1 Base Model

The Core LLM is intentionally selected from high-performing, medium-sized models, with current candidates being **Llama 3 8B**, **Mistral 7B**, or **DeepSeek 7B**. This choice supports the system's objective of distributed inference and modularity, contrasting with monolithic scaling.

### 5.1.2 Quantization

To achieve energy-efficient inference and minimize memory usage, the core model is heavily optimized using custom weight compression techniques:

* **FP4 v3 Macroblocks:** The model weights are quantized using the FP4 v3 codec, which operates via 64x64 macroblocks.
* **Scale Search:** Quantization involves a **32-step scale search** and is performed with a per-block scale.
* **Activation-Aware Tuning:** The system includes the capability for optional activation-aware tuning, and the weights are decoded in shared memory during inference time.

The entire Semantic Core runs efficiently on the **GNUS compute nodes** using the MNN model runtime and GPU acceleration via Vulkan/MoltenVK.

---

## **5.2 Specialist Modules**

The Specialist Modules are smaller, highly optimized models designed to handle specific domains that the Core LLM may struggle with, directly achieving the system's objective of **Modular specialist execution**. This architecture promotes **Specialization over monolithic scaling** by allowing the system to deploy targeted expertise for common challenge areas, thereby enhancing the overall accuracy and reliability of the final output.

### 5.2.1 Grammar Specialist

This module is purposed for text refinement, focusing specifically on **correction & fluency**. It is a relatively small micro-model, ranging from **200M–500M parameters**, ensuring it is lightweight and fast to execute on GNUS nodes. It functions as a **post-processing stage**, refining the text generated by the Core LLM for style, consistency, and linguistic correctness before the final response is aggregated.

### 5.2.2 Math Specialist

Designed to achieve high accuracy on complex numerical and logical problems, this specialist is larger, utilizing **1–3B parameters**. It is **fine-tuned on GSM8K** to ensure robust numerical reasoning, which contributes to the goal of a measurable improvement vs naive single-model baseline. The module is **activated via routing** (e.g., triggered by high numeric density in the prompt), and includes an **optional symbolic fallback** mechanism to guarantee precision when the model's generative output is insufficient.

# 6 Router Design

The Router Layer serves as the critical initial processing point for client requests, acting as the task orchestrator in the system's architecture. Its primary function is to intelligently route incoming tasks to the appropriate Execution Nodes or Specialist Modules, ensuring the system achieves its objective of **Modular specialist execution** and **intelligent task routing**. The router initiates **Task Broadcast** to selected nodes using libp2p.

## 6.1 Initial MVP Router

The initial implementation relies on a **Rule-based detection** system for rapid deployment and predictable routing behavior. This system analyzes the characteristics of the incoming prompt to efficiently determine the required execution path:

* **Numeric density → Math Specialist:** Prompts containing a high density of numerical data or mathematical keywords are routed to the **Math Specialist** for accurate numerical reasoning.
* **Code syntax → Code Specialist (Future):** Queries identified as containing code syntax or complex programming logic are earmarked for routing to a future specialist module.
* **Low complexity → Core Only:** Simple or general-purpose generative prompts, which require only foundational language understanding, are routed exclusively to the **Core LLM** for inference.

## 6.2 Future Router

The roadmap includes upgrading the router to a more sophisticated model-based system to enhance routing accuracy and performance. This future iteration will utilize a **Lightweight transformer classifier**.

* **Model Size:** The classifier will be a relatively small **100M–200M parameter model**, minimizing computational overhead and latency.
* **Function:** This dedicated model predicts the optimal specialist module usage for any given input, thereby improving task-allocation accuracy compared to the initial rule-based system.
