## neoswarm-mnn-llm-header — MNN header path + duplicate/wrong MNN.lib linkage in nested GNUS-NEO-SWARM build
- **Date:** 2026-08-19
- **Error patterns:** MNN/llm/llm.hpp, C1083, Cannot open include file, LNK2019, unresolved external, createLLM, MNN::Transformer::Llm, LNK2005, already defined in MNN.lib, MNN::MNN, bare MNN target, find_library PATH pollution
- **Root cause:** Two related but distinct MNN issues in the same build: (1) NEO-SWARM/SGProcessingManager code assumed `<MNN/llm/llm.hpp>` (nested include path) but the vendored MNN's real installed path (on every platform tested) is `<llm/llm.hpp>` (sibling of `include/MNN/`, not nested under it) — the nested-path assumption was never actually correct anywhere. (2) Separately, GNUS-NEO-SWARM's own `cmake/CommonBuildParameters.cmake` independently defined a redundant, non-namespaced `MNN` CMake target via `find_library(MNN_LIBRARY MNN PATHS "${THIRDPARTY_BUILD_DIR}/MNN/lib" REQUIRED)` missing `NO_DEFAULT_PATH` — this let find_library's default PATH-directory search shadow the intended vendored path, silently resolving to an unrelated local/personal MNN.lib (from an MNN prebuilt-tools install elsewhere on PATH) instead of the project's correct, fully-merged, LLM-enabled MNN.lib that the outer project's `find_package(MNN CONFIG REQUIRED)` already correctly provides as `MNN::MNN`. This caused LNK2019 (missing LLM symbols in the stray lib) for targets that only linked the bare `MNN` target, and LNK2005 duplicate-symbol errors (two different physical files, both literally named MNN.lib) for targets that ended up linking both the stray bare `MNN` and the correct `MNN::MNN` simultaneously.
- **Fix:** (1) Corrected 5 files' `#include <MNN/llm/llm.hpp>` / EXISTS-path-check to `<llm/llm.hpp>` (GNUS-NEO-SWARM/src/core/engine/mnn_inference_engine.cpp, GNUS-NEO-SWARM/test/benchmark/bench_mnn_llm.cpp, SuperGenius/SGProcessingManager/src/processors/CMakeLists.txt + processing_processor_mnn_llm.cpp/.hpp). (2) In GNUS-NEO-SWARM/cmake/CommonBuildParameters.cmake, replaced the unconditional find_library+add_library(MNN UNKNOWN IMPORTED) block with an `if(TARGET MNN::MNN)` branch: when nested (MNN::MNN already exists from the outer project), alias `add_library(MNN ALIAS MNN::MNN)` instead of re-resolving independently; when standalone, fall back to the original find_library path with `NO_DEFAULT_PATH` added to close the same PATH-pollution vulnerability there too.
- **Files changed:** GNUS-NEO-SWARM/cmake/CommonBuildParameters.cmake, GNUS-NEO-SWARM/src/core/engine/mnn_inference_engine.cpp, GNUS-NEO-SWARM/test/benchmark/bench_mnn_llm.cpp, SuperGenius/SGProcessingManager/src/processors/CMakeLists.txt, SuperGenius/SGProcessingManager/src/processors/processing_processor_mnn_llm.cpp, SuperGenius/SGProcessingManager/include/processors/processing_processor_mnn_llm.hpp

## neoswarm-boost-test-gtest — Boost.Test unit_test_main.obj shadows GTest main() via transitive link-order leak from SuperGenius
- **Date:** 2026-08-19
- **Error patterns:** LNK2019, unresolved external symbol, init_unit_test_suite, boost::unit_test::test_suite, libboost_unit_test_framework, unit_test_main.obj, referenced in function main, LNK1120, test_network, test_sg_connectivity, test_sg_client, test_elm, test_pipeline, test_sgprocessing_pipeline
- **Root cause:** SuperGenius's own exported CMake targets `sgns::transfer_proof` and `sgns::processing_proof` (external sibling repo, lib/cmake/SuperGenius/supergeniusTargets.cmake) declare `INTERFACE_LINK_LIBRARIES` that PUBLICLY includes `Boost::unit_test_framework` — almost certainly meant to be PRIVATE/test-only. Because neoswarm_network/neoswarm_api transitively depend on sgns::GeniusSDK_shared -> genius_node -> transfer_proof/processing_proof, the real libboost_unit_test_framework-*.lib (containing unit_test_main.obj, whose main() calls init_unit_test_suite()) lands EARLY in the generated link line — before GTest::Main. MSVC's linker resolves the special `main` entry-point symbol from the first archive object providing it, so Boost's main() wins over GTest's gtest_main.obj, and its call to the never-defined init_unit_test_suite() goes unresolved. NOT caused by any of the affected targets actually using Boost.Test — confirmed all use GTest (`TEST(...)`, `#include <gtest/gtest.h>`) exclusively.
- **Fix:** Reordered the shared `neoswarm_test` CMake macro in GNUS-NEO-SWARM/test/CMakeLists.txt so `GTest::Main`/`GTest::GTest` link BEFORE `${libs}` (was: `${libs} GTest::GTest GTest::Main`). This makes gtest_main.obj always win `main` symbol resolution regardless of what Boost.Test leakage exists transitively in `${libs}`. No source files touched; no Boost.Test->GTest migration needed (targets already used GTest correctly). The actual upstream CMake export bug in SuperGenius was NOT touched — it's in an external, out-of-scope repo (W:\gnus\GeniusNetwork\SuperGenius) and should be fixed at the source by whoever owns it (flagged as a follow-up finding, not a new debug session).
- **Files changed:** GNUS-NEO-SWARM/test/CMakeLists.txt
