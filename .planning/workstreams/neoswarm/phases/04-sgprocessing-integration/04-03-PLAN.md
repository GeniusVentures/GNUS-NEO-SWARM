<objective>
Implement PROC-01: give SGProcessingManager an MNN LLM autoregressive text-generation processor, so SuperGenius compute nodes gain LLM-serving capability directly (D-05's core rationale — "all actual MNN calls happen inside SGProcessingManager"). Per D-07 ("PROC-01 and PROC-02 not necessarily one merged processor") and this phase's own plan-time investigation of dispatch mechanics (`ProcessingManager::Init()` registers exactly one processor factory per `DataType`; `DataType::TENSOR` is already occupied by the extended `MNN_Tensor` from plan 04-02, and `DataType::STRING` is already occupied by `MNN_String`'s distinct BERT-embedding behavior, which this phase must not regress), this plan adds a genuinely new `DataType::LLM` enum value rather than overloading either existing DataType — a purely additive registration with zero risk to the many existing DataType::TENSOR/STRING conformance tests.

The new `MNN_Llm` processor implements the current 6-argument `ProcessingProcessor::StartProcessing()` interface (added by sgproc-render Phase 07's cancellable-execution work) and ports the exact generation-loop pattern already proven correct in NEO-SWARM's own `MNNInferenceEngine::InferViaMnnLlm()` (`MNN::Transformer::Llm::createLLM()`/`load()`/`response()`) — NOT the hand-rolled `InferViaStandardInterpreter` sampling loop, which is the literal duplicate logic D-06 wants eliminated, not moved.

Purpose: Consolidate MNN LLM invocation into SGProcessingManager per D-05/D-06, so both NEO-SWARM's local in-process calls and the wider SuperGenius swarm automatically gain the same LLM-serving capability.
Output: A new, registered, tested `MNN_Llm` processor callable via `DataType::LLM`; `generated/DataType.hpp`/`Generators.hpp` extended with the new enum value and its JSON mapping.
</objective>

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
